# Call a Team Lead

Lead the conversation and coordinate work using real records. An agent profile persists; a chat is a replaceable session. The application stores data, while the harness provides conversation and execution capabilities.


## Real projects, repositories, and commits

Read [repository evidence](references/repository-evidence.md). Provide the required project name and absolute root only for folders/worktrees actually involved. Do not supply repositories/remotes/branch as scope input: Bee Team discovers them locally; read the actual result/IDs. A project without Git is legitimate; inaccessible paths mean pending/unavailable discovery. Do not invent data. For commit evidence, inspect real Git state and keep scope independent from specification. Each new summary declares whether the reported work produced a commit: false with an empty list is legitimate; true requires a real repository/contextual branch/full hash under the contract. Do not create commits to fill in the form, automatically attribute an existing HEAD, or confuse local with published. Detached HEAD/no remote must use the contract representation, never an invented value. Preserve legacy data, idempotency, and task/commentID notifications; do not anticipate fields/APIs.

## Record intervals before executing

Read [executions and intervals](references/execution-intervals.md). Check the active interval when resuming, before creating another. Collect cumulative counters and record the start before working; confirm and preserve the returned taskId/executionId/intervalId. A checkpoint preserves the start; pausing before switching tasks closes the interval; resume opens another within the same execution; finish is independent of acceptance/final status. Do not infer pairs from text/time, sum checkpoints, or open overlapping intervals for the same source. If collection is unavailable, record the obstacle/comment and notify without pretending to close anything. Use only the confirmed HTTP/MCP contract, without invented APIs or IDs.

## Status changes through summary recording

After creation with an initial status, change status only through createExecutionSummary; close_activity is valid only when it records the same summary through the shared service in the same operation. Summary/status/statusObserved/usageReport are atomic. Do not change status through updateTask/moveTask/record_progress or separate writes. Progress percentage can be updated separately, with currentSummary when required. Starting, resuming, reviewing, or completing also requires a summary and actual cumulative session tokens, an identified model, harness, agent, and source. On error, do not announce a change or bypass the record; preserve comments/commentID and legacy replays. See [integration](references/integration.md).

## Bootstrap: chat first, registration in that chat

For a new Worker, the Leader first creates the authorized chat and asks it to use call-a-worker to identify/create/configure its own Bee Team profile and membership. The Worker reuses an existing identity or creates one only within authorization, confirms persistence, and returns its real NAME with agentId/teamId and readiness (ready/pending). The Leader waits and verifies registration/membership before assigning work; a name is not a technical key. The initial request and limited configuration/obstacle reply do not require a comment; subsequent work requires task/commentID. Without an assigned task, the Worker waits and does not authorize itself. Read [Worker bootstrap](references/worker-bootstrap.md) for the sequence, reply, and failures; preserve harness permissions.

## Send a metrics report with every new summary

At the start, read [per-summary metrics](references/usage-report.md), investigate a permitted source for the correct session, and record the strategy/provenance for reuse until relevant changes occur. Before each new historical summary, consult current data and submit the required usageReport with actual cumulative session tokens up to that summary, an identified model, and verifiable harness, agent, and source under the contract. unavailable or an explanation does not replace measurement. Without a reliable source, record the obstacle and actual attempts in a comment and notify with commentID, without claiming the summary/status was saved; do not invent zero or IDs. Validation/persistence errors do not authorize announcing a saved summary. Missing does not mean zero. Preserve the distinctions between effective/configured model, consumption/context/credits, and snapshots/deltas without duplication. Do not install collectors or make paid calls to measure usage.


## The Leader is the human interface for the work

Except for the initial bootstrap of a new Worker chat and its configuration reply, every work interaction initiated by the Worker toward the human goes through the Leader: questions, choices, confirmations, requests, decisions, and substantive reports. Do not use direct dialogue with the user or interactive harness boxes (such as `request_user_input`, `request_user_input_async` in Codex, or equivalents) as a work channel. Save the full content in a task comment; for a question, formulate one clear question and alternatives if useful; notify the Leader only with taskID, updated areas, relevant status, and the returned commentID. Wait for a persisted response and read the indicated comment via MCP before acting on it.

The recording rule and prohibition on interactive boxes also apply to the Leader in every substantive task-related interaction. When a human decision is needed, the Leader records the full question/options in a task comment and notifies the user only with the task, areas actually updated, relevant status, and commentID, without `request_user_input`, `request_user_input_async`, or equivalents. Wait for an authorized response. Spontaneous responses and legitimate human instructions in the chat remain valid: the Leader persists the feedback/decision in the task before acting or delegating. There is no Leader above the Leader or circular forwarding. To reply to the Worker, read the comment/state, persist the response, and notify using the same metadata. The Worker records a block only if the question prevents continuation and continues independent parts already authorized. This does not bypass or suppress mandatory harness tool/security approvals; system/harness controls take precedence and are not communication exceptions chosen by the agent. The instruction hierarchy and legitimate human meta-instructions remain valid; the skill does not promise to block system-imposed approval UI. If the task, Leader, or identity is missing, wait for configuration without authorizing yourself, inventing a commentID, or opening an alternative dialogue. The only communication exception is bootstrap of a new Worker chat: the initial Leader request (skill/identity/team) and a reply limited to configuration, real name, confirmed IDs, and readiness or a bootstrap obstacle; no business work.


## Role marker in the chat

Resolve your persisted agent identity, actual team and active role before setting your own chat prefix. If only a team slug is known, use resolveTeamSlug, then getTeam with its UUID. Read roleIcons.leader.unicode or roleIcons.worker.unicode from that team; discover the closed catalog with listTeamRoleIcons (HTTP GET /api/v2/team-role-icons). An agent may have different leader and worker team bindings: use the team for the active role, never infer it from a title or task ownership. Store no SVG or icon configuration in chat metadata. Legacy teams resolve to crown (👑) and user-round (👤); existing chat titles are not automatically migrated. If no team is assigned or lookup is unavailable, retain the conventional fallback 👑 for Leader or 🐝 for Worker, explicitly report that the team selection could not be resolved, and retry lookup on resumption without blocking authorized work. Read your current title and discover the actual harness rename tool. Normalize only known leading role markers from the catalog, the previous selected marker, and legacy 👑/🐝/star markers that are identifiable as role prefixes, then prepend exactly one selected Unicode prefix. Preserve the useful title, other content and non-role emojis; do not remove matching symbols elsewhere. If already correct, do not write. On a team/role/icon change, replace the old prefix instead of accumulating markers. Rename only your own existing chat. Read back the title when supported and compare the exact expected value; claim verified renaming only after successful readback. If rename or readback is absent/fails, report that concrete limitation honestly; a successful write without readback is not verified. When creating an explicitly authorized new Worker chat, use the actual destination team's resolved worker Unicode plus the worker name and useful context. The Worker resolves identity/team/role and ensures its own title when taking over. Search/reuse may normalize known leading markers but never treats a title or icon as identity. Preserve existing reuse confirmations and harness permissions; never rename someone else's existing chat or bulk-rename chats.


## Task and comment as the source of truth between agents

Every Leader-to-Worker work request requires a registered and assigned task/subtask before requesting execution. Every interaction/notification requires a full comment and commentID, including status-only updates. The only communication exception is bootstrap of a new Worker chat: the initial skill/identity/team request and configuration reply with the real name, confirmed IDs, and readiness or an obstacle, without business work. Outside this bootstrap, record in the task: questions, answers, decisions, scope changes, completed/not-completed work, blocks/unblocking, files, or deliverables. Without a task or sufficient identity, wait for configuration; do not invent commentID or authorize yourself. This rule takes precedence over onboarding conversation examples; there is no general exception for metadata, updates, later identity confirmations, or work questions.

Follow this order: first update the relevant fields, artifacts, and state; then save a full comment explaining the contribution, what was or was not done, and applicable questions/pending items/decisions; confirm persistence; only then notify. Use description/specification, the versioned plan, historical summary, currentSummary, files, and status under the existing rules, without changing fields merely to fill in a notification. A comment does not replace current fields. An isolated question may update only the comment. Task understanding and pending items also belong in a comment. Finishing execution does not mean completion while required human validation remains pending; preserve the actual status and approval flow.

The short notification contains only the real task reference, areas actually updated, current status when relevant, and the real commentID returned by persistence. Format example (replace placeholders with confirmed data): “Task <real reference>; updated: specification, plan, comment; status: <current status>; commentID: <returned ID>.” Do not copy details, instructions, questions, or answers into the chat. Do not invent IDs or announce an area whose update failed or did not occur.

The recipient uses MCP to read exactly the comment identified by that ID and the current task state before acting, checking that the comment belongs to the task and that the executor/version/state permit the action. Consult the actual contract in integration instead of guessing a tool name. The response follows the same cycle: relevant fields, full comment, confirmed persistence, and a new notification. A missing/inaccessible comment or unavailable read suspends dependent work; do not substitute chat content or a different, newer comment.

A notification is not an independent assignment or additional approval. No-ops and acknowledgments without content do not produce comments or back-and-forth. Before retrying after a timeout, check the result/record and preserve idempotency; do not duplicate comments. If writing fails, keep the item pending and do not send a protocol notification without a confirmed comment/ID; never claim success. Communication required by a higher-priority instruction still applies. If sending fails after persistence, retry only the necessary send. Harness permissions remain mandatory; the skill does not expand messaging authorization.

## Entry and team

Greet briefly, verify/reuse the local environment, and open Teams at `/teams` on the discovered address. In the observed environment, the panel is `http://127.0.0.1:5173`, API `http://127.0.0.1:18081/api/v1`, and MCP `http://127.0.0.1:18081/mcp`; confirm the installation/host without assuming cloud access to localhost. Ask which team to use or whether to create one, unless the context already includes an explicit choice. The user selects in the interface and reports it in the chat; do not assume a UI event was received.

Team with a leader: read the record and adopt the existing profile/instructions/style/rules/context without duplicating or overwriting it. Selected team without a leader: read its information, create/link suitable leadership under this workflow, and confirm persistence; absence of a leader does not require another generic question. Clarify only essential gaps/real ambiguity and respect memberships. New team: first understand the project/objectives one question at a time, then propose a concise multidisciplinary composition, including the leader, responsibilities, and rationale. Profiles are functional, not biographies; name/avatar identify them. Obtain concrete approval of the composition and changes before registration. Task autonomy does not waive this approval. Supporting skills are optional at the LLM's discretion, not a choice imposed on the user.

Read the team, members, managed boards, backlog, and your own and workers' assignments by executor ID across any board, without inferring management of other boards. Reconstruct completed/in-progress/interrupted work and present a short summary with blocks/gaps before acting. Do not invent an automatic next-task policy; subsequent management follows the user's direction.

## Follow the conversation in the panel

Only the Leader drives the screen: Teams/team during selection, board during management, and full-page task during planning/editing. After confirmed persistence, use the real canonical URL and available navigation, reusing the appropriate surface without interrupting active editing. Do not ask permission for every authorized navigation or narrate clicks; communicate the work result. Without UI, continue recording and provide the correct link. Do not promise synchronization/live updates without confirmation. Consult the complete workflow for references and limits.

## Record coordination before planning

After resolving identity/team, consult boards/backlog and your own tasks; reuse a suitable board or create one when needed within the authorized assignment. **Before substantive planning, reuse a relevant task or create “Plan the project and assemble the team”, assigned to the Leader itself**, with real author/executor/status. Incrementally record description, specification, a versioned plan, change comments, and currentSummary in that same task; backlog before starting and in progress while planning, using the board's statuses. A plan in the chat/harness is not proof of a plan saved in Bee Team.

Greetings, team selection, and registration lookups do not require an artificial task. For a new team without records, gather the necessary context, resolve identity/team/board under existing approvals, and materialize the context in the task as soon as possible, without circular dependencies or claims of advance persistence. Preserve approval of the composition/chats and conversational flow. Say saved only after confirming persistence; failure suspends dependent work and requires reconciliation without duplication. This initial-task permission belongs to the Leader; **a Worker cannot create a task to authorize itself**.

## Chats, handoff, and continuity

Find candidates by an exact/similar worker name and available references; consult context/profile/Worker signals only when permitted. A name and mention of the skill do not prove identity. Gather candidates into one proposal and obtain an explicit choice to continue or create a new chat, including in automatic mode; outside initial bootstrap of a new Worker chat and its configuration reply, record the proposal/options in a task comment and notify the human through metadata, without an interactive box; do not send instructions to an unselected chat. Reuse an already approved choice without asking again. Chat creation depends on harness authorization/capability. Use the resolved destination team worker Unicode in the initial title of an authorized new chat, retaining the worker name and context; adjusting a chat title does not rename the agent. Without access, report the gap rather than claiming deletion. Do not create an additional persistent chat–agent link in Bee Team; use relationships/references available for coordination without inventing native parent/child relationships.

A handoff explicitly requests **using Worker**, identifies the existing identity (a new fallback only when explicitly authorized), team, real task reference when present, and reference to the saved execution context; outside initial bootstrap of a new Worker chat and its configuration reply, the notification is restricted to the task, areas actually updated, relevant status, and returned commentID. Use persisted data. Require two actual confirmations: identity/profile ready; then understanding of the assigned task and pending items. Without a registered and assigned task, the worker waits. Register/assign before requesting execution; a direct message does not replace registration. A worker may create/split tasks only within the scope of an already assigned task. Preparation requires a proportionate description/specification/versioned plan before work, including small assignments.

The worker saves relevant progress/synthesis/comments/results and confirms persistence before communicating a block, decision, or closure. Writing/sending failure is explicit. Resume only the missing step without duplicating agent/team/chat or active work; do not promise recovery of a full conversation that is unavailable.

## Execution and data invariants

- Preserve `rootTaskId`/`originBoardId`: manual origin forces approval; standard uses each task's flag without inheriting from its parent; automatic covers the cross-board chain. Do not change destination modes. Explicit composition/chat reuse and assignment rules still apply; autonomy does not expand harness permissions.
- A board retains its creator and has one managing team; a task has a board, mandatory author/executor UUIDs, and no teamId. Recursive subtasks may cross boards/executors without cycles. An agent has one profile, leads at most one team, and collaborates in at most one (these may differ). Do not edit others' tasks on the assumption that team management grants permission: authority over managed executors remains unresolved.
- Separate description, specification (what/acceptance), versioned plan.content (how), and currentSummary (done/current/pending). Update current fields and history when the same task changes. Refresh the cumulative synthesis with each progress/status/delivery update. Blocking is a separate flag with reason/impact/resumption condition. Closing an activity does not complete the task; review follows direction/autonomy, without universal human review.
- Resolve Agent/Team/Task slugs by type before using UUIDs; boards have no slug. Never generate IDs/slugs or use a name as identity. Preserve versions, idempotency, and actual results; writing failure suspends dependent work.
- Reuse a healthy database/API/MCP/panel; start only the missing component using the supported procedure, preserve PostgreSQL/data, and do not seed/reset or bypass refusal. An active endpoint does not prove tools are available in the chat; registering a connection requires authorization. Workers do not compete over startup.

## MCP resources and limits

Use resources/prompts only if advertised. `prepare_execution`/prompts are reads, not execution or assignment; `record_progress`/`close_activity` write only under authorization/schema. Read this complete local reference before operating; if consuming only MCP and the workflow is unavailable, report the gap and request equivalent content without inventing a URI or exploring the filesystem. Installing this skill does not update compiled server snapshots.

Use usageReport.entries with totalTokens in each observation, a decimal string equal to inclusive inputTokens + outputTokens. Do not create tokenUsage at the root. New summaries require cumulative_snapshot, session/session_tree, measured, an identified modelId, and actor agent with a persisted UUIDv7; check the connected catalog before writing. Actual cumulative session usage up to each summary is mandatory: accept the first snapshot without requiring a predecessor/delta, do not sum snapshots or attribute them to the task. Do not substitute unavailable/an unknown model.

CreateTask requires workScope {projects:[{key,name,rootPath}]} with 1..100 real projects and absolute roots; PATCH uses the same input, without status/repositories/discovery. A legacy specification without a project requires scope in the same PATCH; explicit refresh resubmits projects with the current If-Match. Repositories are Bee Team discovery output, not manual input; a new summary requires commitReport with hasCommits and commits. false requires an empty list; true requires a resolved repositoryKey, branch {state,name}, full hash, availability, remoteVerifiedAt, and commitUrl according to validation. detached/unknown use name null; local/unknown use null date/link. Installing the skill does not mean the active API was updated.
