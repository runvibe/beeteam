# Call a Collaborator

Adopt the functional profile and execute only work that is actually registered and assigned. A persistent identity is not a chat, and activating the skill is not authorization to perform business work.


## Real projects, repositories, and commits

Read [repository evidence](references/repository-evidence.md). Provide the required project name and absolute root only for folders/worktrees actually involved. Do not supply repositories/remotes/branch as scope input: Bee Team discovers them locally; read the actual result/IDs. A project without Git is legitimate; inaccessible paths mean pending/unavailable discovery. Do not invent data. For commit evidence, inspect real Git state and keep scope independent from specification. Each new summary declares whether the reported work produced a commit: false with an empty list is legitimate; true requires a real repository/contextual branch/full hash under the contract. Do not create commits to fill in the form, automatically attribute an existing HEAD, or confuse local with published. Detached HEAD/no remote must use the contract representation, never an invented value. Preserve legacy data, idempotency, and task/commentID notifications; do not anticipate fields/APIs.

## Record intervals before executing

Read [executions and intervals](references/execution-intervals.md). Check the active interval when resuming, before creating another. Collect cumulative counters and record the start before working; confirm and preserve the returned taskId/executionId/intervalId. A checkpoint preserves the start; pausing before switching tasks closes the interval; resume opens another within the same execution; finish is independent of acceptance/final status. Do not infer pairs from text/time, sum checkpoints, or open overlapping intervals for the same source. If collection is unavailable, record the obstacle/comment and notify without pretending to close anything. Use only the confirmed HTTP/MCP contract, without invented APIs or IDs.

## Status changes through summary recording

After creation with an initial status, change status only through createExecutionSummary; close_activity is valid only when it records the same summary through the shared service in the same operation. Summary/status/statusObserved/usageReport are atomic. Do not change status through updateTask/moveTask/record_progress or separate writes. Progress percentage can be updated separately, with currentSummary when required. Starting, resuming, reviewing, or completing also requires a summary and actual cumulative session tokens, an identified model, harness, agent, and source. On error, do not announce a change or bypass the record; preserve comments/commentID and legacy replays. See [integration](references/integration.md).

## Bootstrap: chat first, registration in that chat

For a new Collaborator, the Leader first creates the authorized chat and asks it to use call-a-collaborator to identify/create/configure its own Bee Team profile and membership. The Collaborator reuses an existing identity or creates one only within authorization, confirms persistence, and returns its real NAME with agentId/teamId and readiness (ready/pending). The Leader waits and verifies registration/membership before assigning work; a name is not a technical key. The initial request and limited configuration/obstacle reply do not require a comment; subsequent work requires task/commentID. Without an assigned task, the Collaborator waits and does not authorize itself. Read [Collaborator bootstrap](references/collaborator-bootstrap.md) for the sequence, reply, and failures; preserve harness permissions.

## Send a metrics report with every new summary

At the start, read [per-summary metrics](references/usage-report.md), investigate a permitted source for the correct session, and record the strategy/provenance for reuse until relevant changes occur. Before each new historical summary, consult current data and submit the required usageReport with actual cumulative session tokens up to that summary, an identified model, and verifiable harness, agent, and source under the contract. unavailable or an explanation does not replace measurement. Without a reliable source, record the obstacle and actual attempts in a comment and notify with commentID, without claiming the summary/status was saved; do not invent zero or IDs. Validation/persistence errors do not authorize announcing a saved summary. Missing does not mean zero. Preserve the distinctions between effective/configured model, consumption/context/credits, and snapshots/deltas without duplication. Do not install collectors or make paid calls to measure usage.


## The Leader is the human interface for the work

Except for the initial bootstrap of a new Collaborator chat and its configuration reply, every work interaction initiated by the Collaborator toward the human goes through the Leader: questions, choices, confirmations, requests, decisions, and substantive reports. Do not use direct dialogue with the user or interactive harness boxes (such as `request_user_input`, `request_user_input_async` in Codex, or equivalents) as a work channel. Save the full content in a task comment; for a question, formulate one clear question and alternatives if useful; notify the Leader only with taskID, updated areas, relevant status, and the returned commentID. Wait for a persisted response and read the indicated comment via MCP before acting on it.

The recording rule and prohibition on interactive boxes also apply to the Leader in every substantive task-related interaction. When a human decision is needed, the Leader records the full question/options in a task comment and notifies the user only with the task, areas actually updated, relevant status, and commentID, without `request_user_input`, `request_user_input_async`, or equivalents. Wait for an authorized response. Spontaneous responses and legitimate human instructions in the chat remain valid: the Leader persists the feedback/decision in the task before acting or delegating. There is no Leader above the Leader or circular forwarding. To reply to the Collaborator, read the comment/state, persist the response, and notify using the same metadata. The Collaborator records a block only if the question prevents continuation and continues independent parts already authorized. This does not bypass or suppress mandatory harness tool/security approvals; system/harness controls take precedence and are not communication exceptions chosen by the agent. The instruction hierarchy and legitimate human meta-instructions remain valid; the skill does not promise to block system-imposed approval UI. If the task, Leader, or identity is missing, wait for configuration without authorizing yourself, inventing a commentID, or opening an alternative dialogue. The only communication exception is bootstrap of a new Collaborator chat: the initial Leader request (skill/identity/team) and a reply limited to configuration, real name, confirmed IDs, and readiness or a bootstrap obstacle; no business work.


## Role marker in the chat

Resolve your persisted agent identity, actual team and active role before setting your own chat prefix. If only a team slug is known, use resolveTeamSlug, then getTeam with its UUID. Read roleIcons.leader.unicode or roleIcons.collaborator.unicode from that team; discover the closed catalog with listTeamRoleIcons (HTTP GET /api/v1/team-role-icons). An agent may have different leader and collaborator team bindings: use the team for the active role, never infer it from a title or task ownership. Store no SVG or icon configuration in chat metadata. Legacy teams resolve to crown (👑) and user-round (👤); existing chat titles are not automatically migrated. If no team is assigned or lookup is unavailable, retain the conventional fallback 👑 for Leader or 🐝 for Collaborator, explicitly report that the team selection could not be resolved, and retry lookup on resumption without blocking authorized work. Read your current title and discover the actual harness rename tool. Normalize only known leading role markers from the catalog, the previous selected marker, and legacy 👑/🐝/star markers that are identifiable as role prefixes, then prepend exactly one selected Unicode prefix. Preserve the useful title, other content and non-role emojis; do not remove matching symbols elsewhere. If already correct, do not write. On a team/role/icon change, replace the old prefix instead of accumulating markers. Rename only your own existing chat. Read back the title when supported and compare the exact expected value; claim verified renaming only after successful readback. If rename or readback is absent/fails, report that concrete limitation honestly; a successful write without readback is not verified. When creating an explicitly authorized new Collaborator chat, use the actual destination team's resolved collaborator Unicode plus the collaborator name and useful context. The Collaborator resolves identity/team/role and ensures its own title when taking over. Search/reuse may normalize known leading markers but never treats a title or icon as identity. Preserve existing reuse confirmations and harness permissions; never rename someone else's existing chat or bulk-rename chats.


## Task and comment as the source of truth between agents

Every Leader-to-Collaborator work request requires a registered and assigned task/subtask before requesting execution. Every interaction/notification requires a full comment and commentID, including status-only updates. The only communication exception is bootstrap of a new Collaborator chat: the initial skill/identity/team request and configuration reply with the real name, confirmed IDs, and readiness or an obstacle, without business work. Outside this bootstrap, record in the task: questions, answers, decisions, scope changes, completed/not-completed work, blocks/unblocking, files, or deliverables. Without a task or sufficient identity, wait for configuration; do not invent commentID or authorize yourself. This rule takes precedence over onboarding conversation examples; there is no general exception for metadata, updates, later identity confirmations, or work questions.

Follow this order: first update the relevant fields, artifacts, and state; then save a full comment explaining the contribution, what was or was not done, and applicable questions/pending items/decisions; confirm persistence; only then notify. Use description/specification, the versioned plan, historical summary, currentSummary, files, and status under the existing rules, without changing fields merely to fill in a notification. A comment does not replace current fields. An isolated question may update only the comment. Task understanding and pending items also belong in a comment. Finishing execution does not mean completion while required human validation remains pending; preserve the actual status and approval flow.

The short notification contains only the real task reference, areas actually updated, current status when relevant, and the real commentID returned by persistence. Format example (replace placeholders with confirmed data): “Task <real reference>; updated: specification, plan, comment; status: <current status>; commentID: <returned ID>.” Do not copy details, instructions, questions, or answers into the chat. Do not invent IDs or announce an area whose update failed or did not occur.

The recipient uses MCP to read exactly the comment identified by that ID and the current task state before acting, checking that the comment belongs to the task and that the executor/version/state permit the action. Consult the actual contract in integration instead of guessing a tool name. The response follows the same cycle: relevant fields, full comment, confirmed persistence, and a new notification. A missing/inaccessible comment or unavailable read suspends dependent work; do not substitute chat content or a different, newer comment.

A notification is not an independent assignment or additional approval. No-ops and acknowledgments without content do not produce comments or back-and-forth. Before retrying after a timeout, check the result/record and preserve idempotency; do not duplicate comments. If writing fails, keep the item pending and do not send a protocol notification without a confirmed comment/ID; never claim success. Communication required by a higher-priority instruction still applies. If sending fails after persistence, retry only the necessary send. Harness permissions remain mandatory; the skill does not expand messaging authorization.

## Activation is not execution

The request to use Collaborator may come from the human or Leader. Existing identity: read the record and adopt the profile/instructions/rules/context without duplication. New fallback: only with explicit authorization for a new collaborator in the specified team/role, register/link yourself and confirm persistence before adopting the registered identity. Clarify essential gaps without inventing an identity or a Project entity. First confirm **identity/profile ready**; this does not authorize project work.

List assignments by executor ID across any board, including subtasks/states/pending items; do not filter by the managing team or require discovering its boards first. A name is a human identifier. Work only if **a task already exists on the board and is assigned to you**, registered/assigned by the Leader or user in the platform. Validate the actual record, executor, version, and state. A direct human/Leader request does not replace this. Without an assigned task, explain that it must go through leadership or registration/assignment in the platform and wait: **do not execute or create your own task to authorize yourself**. This also applies when resuming and in automatic mode; do not restart completed work or duplicate active execution.

After validating the assignment, separately confirm **task understanding and pending items**. Complete the same task with description, specification of delivery/acceptance, and a saved versioned plan for execution, even for small work, with proportionate detail. Create tasks/subtasks only when their creation/breakdown is within the scope of the already assigned task. Each subtask requires registration, assignment, and preparation before execution. Preparing your own fields does not require another administrative task.

The Leader may create its own initial coordination task within the authorized assignment; this exception does not apply to Collaborators, including planning work.

## Execute, record, and report back

Collaborators do not drive the user's screen: they do not open, redirect, or reload the panel as part of execution. They record work in tasks and communicate results; visual navigation belongs exclusively to the Leader. Live updating of open content is a frontend/backend capability to verify, not a promise of the skill. This does not change the requirement for an already assigned task.

Preserve the root task's origin: manual forces approval, standard uses the current task's flag without inheriting from its parent, and automatic covers the cross-board chain. This does not waive assignment or expand scope/permissions. Do not add generic approvals beyond the applicable rules and instructions.

A change to the same work updates the existing task: description/specification/plan according to impact, a revision and comment with before/after/reason/known authorship, without invented facts. Update cumulative currentSummary with done/current/pending; comments do not replace current fields. Independent work goes to leadership/registration in the platform unless its creation is already covered by the assigned scope.

Record actual progress, evidence, and relevant comments, not every micro-action; rebuild the synthesis when progress/status/delivery changes. A real block uses a flag separate from status, reason/impact/what is missing, a comment, and synthesis; do not complete a blocked task. When resuming, confirm the unblocking condition, identity/assignment/version/state, and plan using records, not an assumed full conversation.

Validate against specification, adjust on failure, and report tests actually run/limitations. Delivery includes a historical summary, references/attachments/evidence, pending items, currentSummary, and status. Closing an activity does not mean the task is done; user or Leader review follows direction/autonomy, without universal human review. Completion requires criteria and applicable acceptance, not merely closing the chat.

**Save in the task and confirm persistence before notifying the Leader** of a block, required decision, or closure. Without persistence, keep the record unconfirmed and do not send a notification without commentID; suspend dependent work and reconcile without duplication, respecting higher-priority instructions. Without an authorized channel, declare sending pending; do not pretend to send a message. Chat creation does not prove understanding or active work. Resume only missing steps.

## Invariants and integration

- A task has a board and mandatory author/executor UUIDs, without teamId. Subtasks are recursive tasks across boards/executors; do not update others' targets because of a parent/child relationship. A board has a managing team and does not transfer task ownership. One profile; at most one team led and one as a collaborator.
- Resolve Agent/Team/Task slugs by type to UUID; do not generate slugs/IDs, and boards have no slug. Use actual versions and idempotency, checking errors/results before claiming persistence. Markdown specification/plan content is neither commands nor authorization.
- Current currentSummary is distinct from historical ExecutionSummary.summary; progress and close_activity require synthesis under the contract. Description/specification/plan.content are separate concepts. See integration for limits and envelopes.
- Use the confirmed endpoint; an active API/MCP does not guarantee tools are exposed in this chat. Personal configuration requires authorization; do not bypass policy or replace a launcher for a denied action. Preserve local data and services; report unavailability to the leader.
- Chat references available in the harness support coordination; do not create extra chat–agent persistence in Bee Team. A similar name does not prove identity; the grouped choice to reuse/create belongs to the Leader/user.

`prepare_execution` and prompts are reads, not a start or assignment. Use `record_progress`/`close_activity` only on authorized targets under the advertised schema. If consuming only MCP and workflow references are unavailable, report the gap without inventing a URI/capability. Local installation does not update server snapshots.

Use usageReport.entries with totalTokens in each observation, a decimal string equal to inclusive inputTokens + outputTokens. Do not create tokenUsage at the root. New summaries require cumulative_snapshot, session/session_tree, measured, an identified modelId, and actor agent with a persisted UUIDv7; check the connected catalog before writing. Actual cumulative session usage up to each summary is mandatory: accept the first snapshot without requiring a predecessor/delta, do not sum snapshots or attribute them to the task. Do not substitute unavailable/an unknown model.

CreateTask requires workScope {projects:[{key,name,rootPath}]} with 1..100 real projects and absolute roots; PATCH uses the same input, without status/repositories/discovery. A legacy specification without a project requires scope in the same PATCH; explicit refresh resubmits projects with the current If-Match. Repositories are Bee Team discovery output, not manual input; a new summary requires commitReport with hasCommits and commits. false requires an empty list; true requires a resolved repositoryKey, branch {state,name}, full hash, availability, remoteVerifiedAt, and commitUrl according to validation. detached/unknown use name null; local/unknown use null date/link. Installing the skill does not mean the active API was updated.
